# 套接字标记：告诉你的网络，隧道的报文是做什么用的

你的隧道发送它自己的报文，即那些载着你的流量穿过公网的外层报文，和这台机器发出的其他流量混在一起。对沿途的网络来说，它们只是普通 UDP 报文。以下选项给这些报文打上标记，让路由器和沿途的网络按标记对待它们。

## `--fwmark <number>`（Linux）：这些是隧道自己的报文

防火墙标记是 Linux 内核随连接携带的一个数字。规则随后可以规定：标记为 2 的报文走 WAN 出口，永不进入隧道。不加标记时，为隧道内流量写的路由规则可能把隧道自己的外层报文也送进隧道，形成回环。给外层报文打标记并单独路由，是标准的解法。

在 OpenWrt 上，设好就不用再管：

```
config udpspeeder-simd 'tunnel1'
    option fwmark '2'
    option dscp '46'
```

## `--dscp <0-63>`（各平台）：这些报文是语音级的

DSCP 是每个 IP 报文内部的行业标准优先级字段。46 表示 Expedited Forwarding，即语音。设好之后，沿途行为规范的网络、你的 Wi-Fi、你自己的路由器都会给隧道的报文语音级的队列。在 Wi-Fi 上尤其直接：这个值到达射频的四个空口等级，46 落入语音级，无需进一步配置。

## `--cookie <number>`（FreeBSD）：FreeBSD 侧的等价标记

FreeBSD 的包过滤器按每套接字的数字匹配，与 fwmark 是同一个思路。

## 承诺：要么打上标记，要么拒绝启动

每一个标记都附带一份保证。如果你运行的机器实际上无法把标记放到报文上，比如为另一个操作系统准备的标记，或 Windows 上的 dscp（那里的操作系统会*假装*标记而实际什么也不做），隧道就拒绝启动，并告诉你哪个标记、为什么。它绝不会在报文未被打标、路由规则落空时照常运行。标记为零（默认）表示不动，如同该选项不存在。

隧道的其他流量，即为找到对端而做的名字解析，永不被打标。被标记的解析报文可能被为隧道写的规则路由，导致解析失败。

## 标记到达线缆

测试办法是抓包：每次代码变更，构建系统在 Linux、FreeBSD 和 Windows 机器上启动一个真实的隧道侧发送者，录下离开的报文，再从录像里读回优先级字节。字节与设置的值不完全一致，构建即失败。Windows 的现代 API 通过所谓 *flows* 提供打标，而某些托管机器上 flow 的准入机制并不存在；此时申请的是跳过缺失部分的简版，对一条隧道来说已经够用。细节在仓库的提交历史里。

## 速查表

| 选项 | 标记什么 | 在哪里有效 | 需要权限 |
|---|---|---|---|
| `--fwmark` | 路由与防火墙规则 | Linux | root 或 CAP_NET_ADMIN |
| `--dscp` | IP 优先级字段，及 Wi-Fi 空口 | Linux、FreeBSD、macOS、Windows | 无 |
| `--cookie` | ipfw 匹配 | FreeBSD | 无 |

想要 dscp 的 Windows 用户有一条受支持的替代路径，无需代码：`New-NetQosPolicy`，作为系统策略按程序或端口打标。

*标记不改变隧道发送的任何内容，只改变沿途网络对待它的方式。隧道两端永不需要就标记达成一致。*
